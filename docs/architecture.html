1. 项目定位与总览

TrendRadar 是一个面向个人用户的轻量级热点情报雷达：聚合 11 个中文热榜平台与任意 RSS 订阅源，经关键词或 AI 兴趣筛选、LLM 深度分析与翻译后，生成 HTML 报告并推送到 9 类通知渠道。系统由两个可执行入口组成：

  • trendradar（CLI 引擎）——采集与生产侧：单次进程运行，由外部定时器（cron / GitHub Actions / supercronic）驱动，跑完即退出。
  • trendradar-mcp（MCP Server）——数据消费侧：将爬虫沉淀的 SQLite 新闻库以 27 个 MCP 工具暴露给 Cursor / Cline / Cherry Studio 等 AI 客户端，实现自然语言热点问答、趋势分析、结果再推送。
维度说明
产品形态Python CLI（无常驻进程）+ 可选常驻 MCP HTTP 服务
数据来源热榜：NewsNow 聚合 API（11 平台）；RSS：RSS 2.0 / Atom / JSON Feed 1.1 任意订阅源
AI 能力基于 LiteLLM 统一接口，支持 100+ 提供商（DeepSeek / OpenAI / Gemini / Claude / Ollama 本地模型 / 任意 OpenAI 兼容端点）
存储SQLite 按日分库（主存储）+ S3 兼容远程存储（R2 / OSS / COS / MinIO）+ TXT / HTML 快照
推送渠道飞书、钉钉、企业微信、Telegram、邮件(SMTP)、ntfy、Bark、Slack、通用 Webhook（可接 Discord/Matrix/IFTTT），全部支持多账号（≤3）
部署路线① GitHub Actions 免服务器（7 天试用签到制）② Docker 双容器常驻 ③ 本地 / cron
架构核心特征：引擎是"无状态单次执行 + SQLite 日库"的批处理管线，所有"定时"语义由外部 cron 实现；程序内的 Scheduler 仅决定"本次运行该不该采集 / 分析 / 推送"。MCP Server 与引擎在 Docker 中是两个容器，但代码层面进程内直连（直接 import trendradar 包），通过共享 output/ 卷或 S3 拉取获得数据。

5. 调度系统

"什么时候采集、什么时候分析、什么时候推送、用什么报告模式"由声明式时间线决定，而非硬编码 cron 语义：

数据模型（config/timeline.yaml）

  • presets：4 套预设 —— always_on（全天候增量推）、morning_evening（全天 + 晚间汇总，默认启用）、office_hours（工作日三段式）、night_owl（夜猫子）
  • custom：完全自定义模板
  • 每条 timeline = default（默认行为）+ periods（时间段定义）+ day_plans（日计划引用 periods）+ week_map（周一~周日 → day_plan）+ overlap.policy（重叠策略：报错 / 后者生效）
  • 每个 period 可独立配置：collect / analyze / push 开关、report_mode、ai_mode、once.{analyze,push}、甚至切换 frequency_file / interests_file / filter_method（不同时段用不同关键词或筛选策略）

解析与幂等

  • 启动时 Scheduler 校验时间线合法性（trendradar/core/scheduler.py:313），运行时 resolve() 输出当前时段的 ResolvedSchedule，覆盖 config.yaml 中的默认报告模式
  • 支持跨日时段（如 22:00–02:00）
  • once 语义由 SQLite period_executions 表（execution_date + period_key + action 唯一约束）实现存储级去重
  • schedule.enabled=false 时返回全功能默认配置，回退 config.yaml 行为
设计要点：进程无循环、无 sleep——外部 cron 只负责"叫醒"，Scheduler 决定"醒来后做什么"。这让同一份代码可以无差别运行在手动 / Actions / Docker 三种触发环境下。

6. AI 处理管线

三个 AI 功能（筛选 / 分析 / 翻译）共用同一模型配置段 ai:（LiteLLM），默认 deepseek/deepseek-chat，支持 100+ 提供商与任意 OpenAI 兼容端点（openai/ 前缀 + api_base）。

7. 数据存储架构

为什么按日分库？单日数据量小（热榜 + RSS 千级），日库使清理（按文件名日期删除）、远程同步（按对象键上传当日库）、MCP 回拉（pull_recent_days）都退化为简单的文件级操作，避免引入常驻数据库服务。

8. 通知分发系统

通知子系统是一条五段式流水线（trendradar/notification/dispatcher.py:216 dispatch_all），9 个渠道 × 每渠道最多 3 账号：

  1. 门控：notification.enabled 总开关 + 渠道已配置 + 有内容 + schedule.push + once_push 去重；DISPLAY.REGIONS 控制五区域（hotlist/rss/new_items/standalone/ai_analysis）是否出现，顺序由 region_order 决定。
  2. 翻译前置：对深拷贝的报告数据收集全部可见标题 → translate_batch() 单次批量翻译 → 按 title_locations 回填；失败用原文。
  3. 渲染：整条消息场景用 renderer.py；主流水线由 report/formatter.py: format_title_for_platform 逐行生成 8 种平台格式（来源标签、排名、时间、出现次数、🆕 前缀）；AI 区块由 ai/formatter.py 按渠道渲染。
  4. 拆分（splitter.py）：字节级上限分批 —— 钉钉 20000 / 飞书 29000 / ntfy 3800 / 其他 4000 字节；词组标题 + 第一条新闻必须同批的原子性约束；自动生成统计头（总条数 + AI 分析数）与页脚。
  5. 批头 + 发送（batch.py + senders.py）：每批追加"[第 i/N 批]"（批头空间按最坏 99/99 预留，多字节安全截断）→ requests.post 逐批发送，批间 sleep 3s；邮件走 smtplib（内置 11 家 SMTP 预设），HTML 报告文件作为 multipart 正文。
渠道协议/格式多账号
飞书 / 钉钉 / 企业微信 / SlackWebhook，Markdown/卡片变体; 分隔，配对项（token/chat_id 等）数量必须一致，≤3 账号/渠道
TelegramBot API，HTML
邮件SMTP（gmail/qq/163 等预设），HTML 报告正文
ntfy / BarkHTTP 推送，自托管支持
通用 Webhook自定义 JSON 模板（{title}/{content} 占位），可接 Discord/Matrix/IFTTT
企业微信(个人应用)text 模式可选

跨格式转换（formatters.py）：strip_markdown（先保护 URL 再剥离，供纯文本渠道）与 convert_markdown_to_mrkdwn（Slack 粗体/链接语法转换）。

9. MCP Server 架构

MCP Server（mcp_server/server.py，FastMCP 2.0，实例名 trendradar-news）是数据消费侧的查询/分析/回推服务，供 AI 客户端自然语言驱动。

11. 关键设计决策

决策动机与回答"为什么"
无状态单次执行
程序内无循环，定时全部交给外部 cron		 同一份代码适配手动 / Actions / supercronic 三种环境；进程崩溃即退，无需守护逻辑；调度语义收敛到声明式 timeline.yaml 而非散落各处的 sleep
AppContext 组合根 + Facade
context.py，非全局单例		 消除全局 CONFIG 可变状态；NewsAnalyzer 只依赖一个上下文对象，配置注入（时区/权重/区域顺序）在装配时完成，可测试性优先
SQLite 按日分库 清理 / 远程同步 / MCP 回拉全部退化为文件级操作；单日数据量小，无需常驻数据库服务；远程后端只需"下载-修改-上传"一个文件
URL 标准化去重
utils/url.py normalize_url		 剔除 utm_* 追踪参数与平台动态参数（如微博 band_rank）后按 (url, platform) 建部分唯一索引——同一新闻跨批次/跨参数变体可靠合并，排名轨迹才可累计
两条筛选路径统一收敛 keyword 词频与 AI 兴趣标签最终都产出 stats=[{word,count,titles}] 同一形态，下游分析/报告/通知零感知差异；AI 失败自动回退关键词，可用性优先
AI 结果三重 JSON 容错 LLM 输出不可靠是常态：标准解析 → json_repair 本地修 → AI 自修一次，层级递进控制成本
MCP 进程内直连核心包 避免为 MCP 单独维护一套平行实现；权重公式、词频匹配、通知发送与引擎严格一致；隔离边界放在部署层（独立容器 + 共享卷）而非代码层
存储级幂等
period_executions / ai_filter_analyzed_news		 once 推送去重、已分析新闻去重都落在 SQLite 唯一约束上，进程重启 / 重复执行不产生副作用，也不重复消耗 token
字节级消息分批 各渠道消息上限差异大（钉钉 20KB vs ntfy ~3.7KB），拆分器按渠道上限 + 批头预留 + 多字节安全截断，保证"词组标题与首条新闻同批"的可读性原子约束
