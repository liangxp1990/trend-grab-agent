1. 目标与边界

目标：为 TrendRadar 提供一个常驻 Web 管理平台，将"手改 YAML + 看日志 + 翻文件"的操作体验升级为界面化管理，覆盖四大数据能力：

能力域内容取代的现状
配置管理数据源 / 调度时间线 / AI 兴趣与模型 / 通知渠道的可视化编辑，版本历史、diff、回滚、变更审计、敏感项脱敏手改 config.yaml + timeline.yaml + 词表/提示词文件
运行监控任务执行历史、成功/失败时间线、手动触发、实时日志流（WebSocket）、数据源健康度（哪些平台抓取频败）docker logs / 无任务级记录
报告中心历史 HTML 报告在线浏览（按日期/模式检索）、推送记录与各渠道送达状态追溯翻 output/html/ 目录
数据浏览分析热榜/RSS 历史查询、关键词热度趋势曲线、排名轨迹、平台对比、全文搜索MCP 工具（面向 AI 客户端而非人）

边界（本规划不做）：

  • 不做多租户 SaaS：无注册流程、无计费、无公网多用户运营。单管理员（初始密码由环境变量注入）。
  • 不重写引擎：trendradar 包的抓取/分析/推送管线保持现状，平台通过适配层调用。
  • 不引入消息队列 / K8s：单容器部署，调度器内置于平台进程。

演进预留（中期兑现点，本期内只做结构性预留不做功能）：

  • 平台库所有业务表带 owner_id（默认 1），建 users 表与 JWT 载荷结构；
  • ORM 用 SQLAlchemy 2.0 + Alembic 迁移，保持 PostgreSQL 平滑切换能力（SQLite 起步）；
  • API 统一 /api/v1 前缀，为未来开放 API Token 做准备。

2. 现状约束与设计原则

必须尊重的现状约束

  • 引擎是无状态单次进程：NewsAnalyzer.run() 阻塞执行、print 输出、本地模式自动开浏览器——平台调用需要隔离与捕获。
  • 配置以文件为真相源：loader.py 只认 YAML 文件 + 环境变量覆盖。
  • 数据在 SQLite 日库：output/news|rss/{date}.db，按日分库、引擎独占写。
  • 双入口并存：CLI 与 MCP Server 必须继续可用，平台不能破坏它们。

设计原则

  • 不侵入引擎：平台化改造集中在新增的 webapp/ 包与极少量引擎适配点（headless 旗标、日志句柄注入），引擎保持可独立 CLI 运行。
  • 平台与数据分离：平台元数据（新 platform.db）与引擎数据（日库）物理分库，各自单一写者，无锁冲突。
  • 复用优先于重写：数据查询/分析直接 import mcp_server/services 与 trendradar/core（MCP 已验证的分析能力搬进 UI）。
  • 每一步可回退：配置版本化 + 引擎零改造，随时退回 CLI 模式。

4. 核心设计决策

#决策理由（回答"为什么"）
D1 配置真相源迁移至平台库
YAML 降级为投影/导出格式		 平台化的核心是配置在线可管理：版本化、审计、回滚、多用户归属都要求 DB 作为 source of truth。若继续以 YAML 为真相源，UI 编辑会退化为"带界面的文本编辑"（现状 docs/index.html 已证明天花板）。config_versions 表存结构化 JSON，敏感项（webhook/api_key）加密列存储。
D2 DB → YAML 投影 + 子进程执行
而非改造引擎支持内存配置		 引擎保持"文件驱动 + 零改造"：平台在触发任务前把配置版本渲染为 run/{version}/ 下的完整文件集（YAML + 词表 + 提示词），以 --config 指给子进程。执行期配置天然冻结（本来就该如此）；引擎崩溃被进程边界隔离；CLI 模式读原 config.yaml 完全不受影响。改造量集中在投影器（DB JSON → 引擎文件布局），一处收敛。
D3 调度内置（APScheduler）取代 supercronic 调度必须可 introspect：UI 要展示"下次运行时间 / 上次结果 / 暂停 / 立即执行"。外部 cron 无法提供这些。APScheduler 与 FastAPI 同进程，任务触发走统一 JobService（与手动触发同一条路径），互斥锁防重叠。
D4 分析能力抽公共层，MCP 与 Web 同源 数据浏览的分析逻辑（趋势/对比/聚合/搜索）大量存在于 mcp_server/tools/analytics.py（2639 行）。抽出 analytics_core/ 公共层供 MCP 与 Web 同时 import，避免两套口径——这是 MCP"进程内直连"决策（见架构文档第 11 节）的自然延伸。
D5 平台库与数据日库物理分离 引擎独占写日库（现有 upsert/轨迹逻辑不动），平台独占写 platform.db，跨库只读查询。消除 SQLite 并发写问题（各库开 WAL），也保证"平台挂了引擎数据完好"的可回退性。
D6 单管理员 + 结构性多用户预留 按用户决策"单机起步、预留演进"：一期只有 env 注入的管理员账户，但 users 表、JWT 载荷、业务表 owner_id、/api/v1 版本化从第一天就就位——未来开多用户是"放开注册页"而非重构。

5. 平台数据模型

新增 platform.db（SQLite + WAL，SQLAlchemy 2.0 ORM + Alembic 迁移）：

表关键字段说明
usersid, username, password_hash, role(admin/viewer), is_active, created_at一期仅一条 admin 记录；role 为 RBAC 预留
config_versionsid, owner_id, version, content(JSON 全量), secrets(JSON 加密列), checksum, comment, created_by, created_at配置真相源；敏感项独立加密存储，API 返回脱敏视图
config_activeowner_id, current_version_id当前生效版本指针；回滚 = 移指针 + 重新投影
job_runsid, trigger(cron/manual/api), config_version_id, status(pending/running/success/failed/cancelled), started_at, finished_at, duration_ms, exit_code, error_summary, log_path任务级执行记录（区别于引擎数据层的 crawl_records）
job_channel_resultsjob_run_id, channel, account_idx, success, batch_count, error各渠道送达状态——引擎 dispatcher 返回结果由执行器落库
audit_logsid, user_id, action(config.update/job.trigger/login…), detail(JSON), ip, created_at变更审计，配置回滚的依据链
schedulesid, owner_id, name, cron_expr, enabled, next_run_at, last_run_status平台调度定义（从 timeline.yaml 首次导入生成）

引擎侧唯一改造点：通知 dispatcher 把渠道级结果以结构化形式输出（写入约定路径的 JSON），执行器读取落库；--headless 旗标关闭浏览器与交互式输出。两处均为增量，不改变默认行为。

6. 后端 API 概要

端点方法说明
/api/v1/auth/login|logout|mePOST/GETJWT 签发/刷新/身份
/api/v1/configGET/PUT读写当前生效配置（结构化 JSON，敏感项脱敏返回；PUT 生成新版本）
/api/v1/config/versionsGET版本列表 + diff（任意两版本 JSON diff）
/api/v1/config/versions/{id}/rollbackPOST回滚指针并重新投影
/api/v1/config/validatePOST保存前校验（复用 loader 校验 + 渠道配对检查）
/api/v1/config/test-notificationPOST发送测试通知（复用 --test-notification 管线）
/api/v1/scheduleGET/PUT调度定义 CRUD、启用/停用、下次运行时间
/api/v1/jobsGET/POST执行历史（分页/筛选）；POST 手动触发（指定配置版本可选）
/api/v1/jobs/{id} · /logsGET任务详情（渠道送达结果）/ 日志内容（支持 offset 增量拉取）
/api/v1/ws/statusWS运行中任务的实时状态与日志流
/api/v1/data/news|rssGET历史查询（日期/平台/关键词/分页）——复用 mcp_server/services
/api/v1/data/trends|compare|searchGET热度趋势、平台对比、全文搜索——复用 analytics 公共层
/api/v1/data/platforms/healthGET源健康度（crawl_source_status 聚合：成功率/最近失败）
/api/v1/reportsGET报告索引（扫描 output/html/{date}/，含元数据）
/api/v1/push-recordsGET推送记录（period_executions + job_channel_results 聚合）
/api/v1/system/status|versionGET存储状态、引擎/MCP/平台版本（复用 check_version）

静态资源：/reports/* 托管 output/html（iframe 预览报告）、/ 托管 Vue SPA。所有 API 走 JWT；错误结构复用 mcp_server/utils/errors.py 的 code + suggestion 风格。

8. 实施路线图

里程碑周期验收标准
M1 骨架与执行底座~2 周登录可用；手动触发一次任务成功落库 job_runs 并可查看日志；引擎 CLI 行为与改造前完全一致（回归）
M2 运行监控 + 调度~2 周APScheduler 按 timeline 定时执行；仪表盘展示任务状态/下次运行；WebSocket 实时日志；渠道送达状态可见
M3 配置管理 + 报告中心~2 周全部配置段表单化编辑并生效（改 RSS 源 → 下次任务即抓新源）；版本 diff/回滚可用；报告在线预览；敏感项脱敏
M4 数据浏览分析~2 周趋势曲线/平台对比/搜索与 MCP 工具结果一致（同源验证）；源健康度热力图上线
排序依据：M1/M2 先建"执行底座与可观测性"而非先做配置管理——因为配置管理依赖执行器验证生效（"改了配置 → 看到任务按新配置跑"是管理闭环的验收链），且监控是其余所有页面的数据前提。

9. 风险与对策

风险对策
引擎 run() 阻塞、print、本地开浏览器，不适配服务端调用子进程执行 + --headless 旗标 + stdout/stderr 重定向；不在线程内直接调 run()，保留 CLI 语义
调度重叠 / 手动与定时并发冲突JobService 进程内互斥锁（同刻仅一个引擎实例）；重复触发返回 409 + 当前任务指针
配置投影与 DB 版本不一致（编辑发生在任务运行中）触发时快照投影、执行期冻结；运行中标记 config_locked，UI 提示"任务运行中，保存将于下次任务生效"
敏感信息（webhook/token/api_key）入库泄露独立加密列（Fernet，密钥来自 env）；API 一律脱敏返回（尾 4 位）；审计日志记录变更不记录值
SQLite 平台库并发写（WS 推送 + API 写）WAL 模式 + 单写连接池；平台库写频极低（任务分钟级），实测无压力；PG 演进路径已留
分析逻辑从 mcp_server 抽公共层引发 MCP 回归M4 单独执行抽取 + 为 MCP 27 工具补契约测试（现有行为快照对比）后再切换引用
暴露端口被公网访问（原架构全绑 127.0.0.1）保持默认绑 127.0.0.1；公网访问文档引导走反代 + HTTPS；登录限速 + JWT 过期
timeline 调度语义双轨（supercronic vs APScheduler）迁移期并存但互斥文档声明；平台部署模板默认不启用 supercronic；提供"调度导入"一键从 timeline.yaml 生成 schedules
MCP 配置一致性断裂（真相源迁 DB 后，共享卷 config/ 中的 YAML 陈旧，MCP 的 get_current_config / send_notification 读到过时配置）投影器双写：配置每次生效时，除渲染 run/{version}/ 外，同步渲染一份"当前生效配置"到共享 config/ 卷（config.yaml 由投影器单一写者更新，敏感项从加密列解密注入）。MCP 容器零改造即读到最新，CLI 回退模式同样受益
投影 YAML 明文敏感信息落盘（DB 加密存储的 webhook / api_key，投影为引擎可读的 YAML 时必然解密）run/ 目录权限 0700、投影文件 0600；任务结束即时清理敏感投影文件，保留脱敏副本供排障；容器以非 root 用户运行；审计日志记录投影生成与清理事件
旧 supercronic 容器与新平台调度器并行导致日库双写JobService 启动时检测共享卷中 supercronic crontab 是否仍启用，存在则仪表盘醒目告警并阻塞首次调度（机制性防护，超越文档声明）

10. 兼容性与迁移

  • CLI 模式不变：python -m trendradar 继续读 config/config.yaml，适合不想部署平台的用户——引擎零侵入保证这一点。
  • 首次接入平台：安装向导扫描现有 config.yaml → 导入为 config_versions v1 → 生成 schedules → 原文件只读封存（作为回退备份）。
  • Docker Compose 变化：trendradar 容器（supercronic）→ trendradar-web 容器；trendradar-mcp 保留；共享卷不变（config/ + output/）。旧用户可选择不升级。
  • MCP 配置同步：配置真相源迁入 DB 后，共享卷 config/config.yaml 的写权移交平台投影器——每次配置生效（保存 / 回滚）双写 run/{version}/ 与共享卷当前配置，保证 MCP 的配置读取 / 通知发送 / CLI 回退三条路径永远与平台所见一致（配置闭环）。
  • GitHub Actions 用户：平台与该路线互斥（平台需要常驻进程），文档中明确分叉指引。
  • 回退路径：任意时刻停止 web 容器、恢复 config.yaml 即回到纯 CLI——配置版本可导出为标准 YAML 文件集。
本规划的三个不妥协：① 引擎可独立 CLI 运行（零侵入）；② 配置版本化可回滚（管理界面的信任底线）；③ MCP 与 Web 分析同源（不养两套口径）。所有设计决策冲突时优先满足这三条。
